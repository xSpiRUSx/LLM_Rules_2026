# Стиль BSL-кода

## Общие правила

- Код пишется на русском синтаксисе BSL.
- Имена процедур, функций и переменных должны отражать бизнес-смысл.
- Не использовать сокращения, если они не являются устоявшимися в проекте.
- Не использовать имена из глобального контекста 1С для переменных.
- Не использовать отрицательные булевы имена вроде `НеПроводить`, если можно назвать положительно.
- Не использовать магические числа — вынести в переменную или константу.

## Форматирование

- Одна инструкция — одна строка.
- Не писать сложные условия в одну строку.
- Длина строки — до 180 символов, если перенос не ухудшает читаемость.
- В сложных условиях использовать промежуточные переменные.
- Вызов проектного метода с позиционными параметрами должен помещаться в одну строку длиной до 180 символов. Если вызов не помещается, сначала упрости аргументы с помощью осмысленных промежуточных переменных. Если этого недостаточно, не раскладывай позиционные параметры по строкам: объедини логически связанные параметры в структуру с фиксированным составом либо декомпозируй метод.
- Для платформенных, библиотечных и других неизменяемых интерфейсов допускается перенос параметров по стандарту 1С. Не изменяй внешний интерфейс только ради однострочного вызова.
- Тело метода из 10 и более непустых строк разделять пустыми строками на смысловые блоки. Блок — это группа инструкций с одной целью, например: подготовка данных, ветвление, заполнение полей объекта или формирование результата. Тело такого метода без единой пустой строки — дефект форматирования, а не стилевой выбор.

## Текст запроса внутри строкового литерала

В BSL текст запроса — обычная строка, и escape-последовательностей в ней нет. `\t`, `\n`, `\r`, `\"` внутри литерала попадают в текст запроса буквально, двумя символами, и ломают его.

- Отступ поля в запросе набирается настоящими пробелами или табуляцией после `|`.
- Перенос строки — новая строка литерала с `|`, а не `\n`.
- Кавычка внутри запроса удваивается: `""`, а не `\"`.

Это правило особенно важно, когда текст запроса формируется программно или передается через инструмент записи: экранирование, нужное транспорту, не должно попасть в файл. После правки текста запроса убедись, что в модуле нет последовательностей `\t` и `\n` внутри литералов, и проверь сам запрос средствами проекта.

## Сложность

- Метод больше 100 строк — кандидат на декомпозицию.
- Метод больше 200 строк — недопустим, кроме больших текстов запросов, типового или сгенерированного кода.
- Вложенность больше 4 уровней — нужно упростить.
- Больше 4 параметров метода — использовать структуру параметров или пересмотреть интерфейс.
- Предпочитать ранний выход:

```bsl
Если Отказ Тогда
	Возврат;
КонецЕсли;

Если Не ЗначениеЗаполнено(Контрагент) Тогда
	Возврат;
КонецЕсли;
```

## Строки

Для сложного формирования строк использовать `СтрШаблон()`.

Предпочтительно:

```bsl
ТекстСообщения = СтрШаблон(
	"Не заполнен контрагент в документе %1.",
	ДокументСсылка);
```

Нежелательно:

```bsl
ТекстСообщения = "Не заполнен контрагент в документе " + Строка(ДокументСсылка) + ".";
```

## Пользовательские сообщения

Не использовать `Сообщить()`.

Предпочитать `СообщениеПользователю` или обертки БСП, если БСП есть в проекте:

```bsl
ОбщегоНазначения.СообщитьПользователю(НСтр("ru = 'Не заполнен контрагент.'"));
```

или

```bsl
Сообщение = Новый СообщениеПользователю;
Сообщение.Текст = НСтр("ru = 'Не заполнен контрагент.'");
Сообщение.Поле = "Объект.Контрагент";
Сообщение.Сообщить();
```

## Исключения

Запрещено:

```bsl
Попытка
	// код
Исключение
КонецПопытки;
```

Пустой обработчик исключения запрещен.

Не оборачивать обычные чтения и записи базы в `Попытка ... Исключение`, если нет понятной стратегии обработки.

Если исключение перехватывается, нужно:

- либо добавить осмысленное сообщение пользователю;
- либо записать диагностическую информацию, если логирование требуется задачей;
- либо пробросить исключение выше;
- либо выполнить откат/компенсацию в транзакционном сценарии.

## Запрещенные конструкции

Этот пункт нарушать можно только с явным обоснованием:

- `Выполнить()`;
- `Вычислить()`;
- `Сообщить()` для пользовательских уведомлений;
- `ЗаписьЖурналаРегистрации()` без задачи на логирование;
- hardcoded-пароли, токены, ключи API;
- COM-объекты и Windows-only решения, так как должна работать кроссплатформенность;
- запросы и серверные вызовы внутри циклов;
- изменение публичных экспортных сигнатур;
- методы сверх ограничений раздела «Сложность»;
- пустые `Исключение`;

Пустой `Исключение` и секреты в коде — одновременно критичные запреты. Для них обоснования недостаточно: нужна отдельная явная команда пользователя.

## Комментарии

Комментарии нужны для объяснения причины, ограничения или неочевидного решения.

Хороший комментарий:

```bsl
// Используем дату сеанса, чтобы расчет совпадал с рабочей датой пользователя.
ДатаРасчета = ТекущаяДатаСеанса();
```

Плохой комментарий:

```bsl
// Получаем дату
ДатаРасчета = ТекущаяДатаСеанса();
```
