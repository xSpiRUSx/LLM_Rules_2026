# Архитектура 1С

## Сначала возможности платформы и БСП

Прежде чем писать собственную реализацию, проверь, не решает ли задачу готовый механизм платформы 1С:Предприятие или БСП.

Порядок проверки:

1. Проверь документацию платформы для актуальной версии и режима совместимости проекта.
2. Проверь БСП, если задача похожа на библиотечную.
3. Проверь существующие реализации в самом проекте.

Собственная память модели не является доказательством отсутствия механизма: именно специализированные возможности платформы чаще всего отсутствуют или устарели в знаниях модели. Отсутствие механизма фиксируется только по документации, доступной в текущей задаче.

Если подходящий механизм найден — он становится основой решения. Свой код пишется только для связывания, параметров и проектной обвязки. Неудобство найденного механизма (непривычный API, дополнительное преобразование, необходимость тонкой обертки) не является основанием писать параллельную самописную реализацию.

Если механизм закрывает задачу лишь частично, это значимая развилка: покажи выбор «механизм платформы плюс обертка» против «полностью своя реализация» с последствиями каждого варианта и запроси решение
Отказаться от найденного механизма можно только по фактическому основанию: несовместимость с версией платформы или режимом совместимости, либо подтвержденное документацией несоответствие сути требования.

## Размещение логики

Бизнес-логика должна быть на сервере.

Допустимые места:

- общий серверный модуль;
- модуль объекта;
- модуль менеджера;
- подписка на событие;
- специализированный общий модуль подсистемы.

Нежелательные места:

- клиентский обработчик формы;
- обработчик команды формы с большим объемом бизнес-логики;
- общий модуль без понятной зоны ответственности;
- дублирующий код в нескольких формах.

## Клиент и сервер

Клиентский код должен:

- управлять интерфейсом;
- читать значения формы;
- вызывать серверные методы;
- показывать результат пользователю.

Серверный код должен:

- проверять бизнес-условия;
- читать и писать данные;
- выполнять запросы;
- выполнять массовую обработку;
- формировать движения;
- выполнять интеграционную логику, если это серверная интеграция.

## `&НаСервере` и `&НаСервереБезКонтекста`

Использовать `&НаСервереБезКонтекста`, если метод не обращается к данным формы напрямую.

Предпочтительно:

```bsl
&НаКлиенте
Процедура ОбработатьКоманду(Команда)

	Параметры = Новый Структура;
	Параметры.Вставить("Контрагент", Объект.Контрагент);

	Результат = ПолучитьДанныеНаСервере(Параметры);

КонецПроцедуры

&НаСервереБезКонтекста
Функция ПолучитьДанныеНаСервере(Параметры)

	// серверная логика

КонецФункции
```

Использовать `&НаСервере` только если метод действительно читает или меняет реквизиты формы.

## Запись объектов

Проверки записи должны работать:

- при интерактивной записи из формы;
- при программной записи;
- при обмене;
- при фоновой обработке, если объект может записываться там.

Не полагаться только на клиентскую проверку формы.

## Проведение документов

При изменении проведения:

- определить все регистры, куда документ делает движения;
- проверить влияние на перепроведение;
- проверить отрицательные остатки, если они контролируются;
- проверить движения при отмене проведения;
- проверить программное проведение;
- проверить права пользователя;
- проверить производительность запросов.

Не менять движения документа без отдельного описания последствий.

## Транзакции и блокировки

Не открывать транзакцию без понимания, есть ли уже внешняя транзакция.

В транзакциях:

- не выполнять долгие операции;
- не вызывать внешние HTTP-сервисы;
- не показывать пользователю диалоги;
- не выполнять лишние запросы;
- соблюдать единый порядок блокировок.

## Фоновые задания

Операции, которые могут выполняться дольше 10 секунд, рассматривать как кандидаты на фоновое задание.

Фоновое задание должно иметь:

- понятные параметры;
- контроль прав;
- логирование результата, если это важно;
- способ сообщить пользователю об ошибке;
- защиту от повторного запуска, если это критично.
